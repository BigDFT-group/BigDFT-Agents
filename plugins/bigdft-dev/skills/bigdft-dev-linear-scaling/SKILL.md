# Linear-Scaling Optimization Internals

This is a mechanics reference, not an introduction to linear-scaling DFT -- it assumes you already know what support functions (TMBs) and a density kernel are. Every claim here is grounded in a specific file:line in `bigdft-suite` (paths relative to the `bigdft/` package root unless noted) and was verified by reading the source, not inferred from documentation. It grew out of a real debugging session chasing a restart-energy discrepancy (see the "Open question" section at the end) -- update it as that investigation progresses.

## The outer loop (`src/linear/linearScaling.f90`, subroutine `linearScaling`)

The whole calculation is one loop: `outerLoop: do itout=istart,nit_lowaccuracy+nit_highaccuracy`. Each outer iteration does one round of support-function optimization (`getLocalizedBasis`) followed by one round of kernel/density optimization (`scf_kernel`, an internal contained subroutine wrapping the mixing loop `kernel_loop: do it_scc=1,nit_scc`).

### Three `target_function` values, two `nlevel_accuracy` regimes

- `TARGET_FUNCTION_IS_TRACE`, `TARGET_FUNCTION_IS_ENERGY`, `TARGET_FUNCTION_IS_HYBRID` (from `public_enums`).
- `input%lin%nlevel_accuracy == 2`: the "normal" two-level scheme. `itout==1` calls `set_optimization_variables` (`src/linear/initAndUtils.f90:1228` area) which sets `target_function=TARGET_FUNCTION_IS_TRACE` while `.not. lowaccur_converged`, or `TARGET_FUNCTION_IS_ENERGY` once it is. Each subsequent `itout` calls `check_whether_lowaccuracy_converged(itout, nit_lowaccuracy, input%lin%lowaccuracy_conv_crit, lowaccur_converged, pnrm_out)` (`linearScaling.f90:394`) to decide whether to flip `lowaccur_converged` from false to true -- this is a real, explicit convergence check on the low-accuracy phase.
- `input%lin%nlevel_accuracy == 1` ("hybrid", `lin_general.hybrid: Yes` in input.yaml): `set_variables_for_hybrid` (`initAndUtils.f90:960`) is called **once**, only at `itout==1` (`linearScaling.f90:411: else if (input%lin%nlevel_accuracy==1 .and. itout==1)`), and sets `target_function=TARGET_FUNCTION_IS_HYBRID` unconditionally. **`target_function` is never reassigned away from `HYBRID` anywhere in this file for the `nlevel_accuracy==1` path.** There is no "transition to high accuracy" for hybrid mode in the sense the two-level scheme has one -- verified by grepping every assignment to `target_function` in the file; the only other assignment sites are inside the `nlevel_accuracy==2`-gated `set_optimization_variables`/`set_optimization_variables` (line 436, itself gated `if (input%lin%nlevel_accuracy==2)`) call. Don't go looking for a hybrid-mode phase transition; it doesn't exist as a separate concept.
- **What actually ends a hybrid-mode run**: `check_for_exit` (`linearScaling.f90:2249`), specifically its `nlevel_accuracy==1` branch (line 2272): `if (pnrm_out < input%lin%highaccuracy_conv_crit) then infocode=0; exit_outer_loop=.true. else if (itout==nit_lowaccuracy) then exit_outer_loop=.true.` -- note the iteration-cap branch does **not** set `infocode=0`, so it stays at its default of `1` (`linearScaling.f90:382`). This is exactly the `infocode: 1` after hitting the iteration cap seen in real divergent restarts. `pnrm_out` is the density/potential residual from the kernel mixing loop (`printSummary`, `linearScaling.f90:2285`, prints it as `delta`). So for hybrid mode, convergence is purely "is the density residual small enough yet," checked fresh every outer iteration, with no lower-accuracy-phase bookkeeping at all.
- For `nlevel_accuracy==2`, `check_for_exit`'s other branch (line 2254) only evaluates once `lowaccur_converged`, and distinguishes `alpha_mix_highaccuracy /= 0` (checks `pnrm_out<highaccuracy_conv_crit` or `cur_it_highaccuracy==nit_highaccuracy`) from the `==0` case (checks `energyDiff` instead) -- a real, separate exit criterion from the low-accuracy one, unlike hybrid mode which only has the one.

### `can_use_ham` -- reuse the SF-optimization Hamiltonian for kernel optimization, or not

`linearScaling.f90:706-727`: for `TARGET_FUNCTION_IS_TRACE`/`_ENERGY`, `can_use_ham` gets forced `.false.` if any `input%lin%potentialPrefac_lowaccuracy/highaccuracy(itype) /= 0.d0` -- i.e. this checks the **raw input value** (whether confinement was requested as nonzero, `-1` "automatic" included, since `-1 /= 0`), not the actually-applied confinement magnitude. **The `TARGET_FUNCTION_IS_HYBRID` case of this same check is entirely commented out** (lines 720-726). So for hybrid mode this override never runs, and `can_use_ham`'s value is purely whatever `getLocalizedBasis` last set it to (see below) -- another instance of the hybrid-mode code path having a check the other two modes get that was apparently never migrated over.

## Confinement mechanics

- Per-orbital confinement lives in `confpot_data` (`liborbs/src/potential.f90:22`): fields `prefac` (the value actually used in the confining potential), `damping`, `potorder`, `hh`, `rxyzConf`, `ioffset`.
- Constructor `confinement_data(confpotorder, potentialprefac, lr, rxyz)` (`potential.f90:54`) **unconditionally sets `damping = 1.0_gp`** (line 70) whenever a fresh `confpot_data` is built.
- `set_confdatarr` (`src/linear/initAndUtils.f90:1104`) computes `prefac` per orbital/atom-type from `input%lin%potentialPrefac_lowaccuracy`/`_highaccuracy(itype)`: negative -> "automatic", `prefac = 20.d0/locrad(ilr)**4`; otherwise the literal input value (`0.0` for explicit zero-confinement). It does **not** multiply by `damping`. It also prints, unconditionally regardless of `frag_calc`, the per-process `max diff damping` (max pairwise difference of `confdatarr(:)%damping` across local orbitals) and `confdatarr(1)%damping` as `damping value` -- useful uniformity check, already confirmed uniform (`0.00E+00` after the fix below) across every orbital in every run tested so far.
- **The 2015 bug** (git blame `0b8f28f57a`, "corrected a bug in the automatic setting of the prefactor for the confinement", 2015-01-19): before this commit, `set_variables_for_hybrid` had its own inline per-orbital loop ending in `confdatarr(iorb-orbs%isorb)%prefac=prefac*damping_factor` -- the *only* one of three near-identical loops (the other two, in `set_optimization_variables`'s high/low-accuracy branches, never multiplied by damping) that did this multiply. The commit consolidated all three into the shared `set_confdatarr`, which follows the two-out-of-three behavior (no damping multiply) -- silently dropping the multiply for the hybrid case. `damping_factor` is still received as an argument by `set_variables_for_hybrid` and is fully correctly computed (see restart section below); it's just never applied. **This was still present, unfixed, on `devel` as of 2026-09-29.**
- **Restart-time damping**: `tmb%damping_factor_confinement` (scalar field on `tmb`, declared `types.f90:299`). Default `1.d0`, set in `cluster.f90:720` ("will be modified in case of a restart"). Computed for real in two places, both following the identical formula `tt = exp(max_shift*3.465735903d0) - 1.d0` (0 when nothing moved, saturating to 1 by `max_shift~0.2` Bohr), `min(tt, 1.d0)`:
  - `readmywaves_linear_new`/`reformat_one_fragment` (`src/modules/io.f90`, formula at what was line 3433 pre-fix) -- the **disk restart** path (`INPUT_PSI_DISK_LINEAR`), confirmed via real historical logs to be what *both* a "wavelet restart" and "cube/disk restart" from a real bug report actually used (both printed identical `Policy: Reading Wavefunctions from disk`; the wavelet-vs-cube distinction referred to in that report was never identified at the input/code level during this investigation -- see open question).
  - `input_memory_linear` (`src/init.f90`, formula at what was line 851 pre-fix) -- the **wavelet/in-memory restart** path (`INPUT_PSI_MEMORY_LINEAR`). Not used by the runs actually investigated, but present and worth knowing about.
  - `max_shift` is computed by comparing atom positions embedded in the restart file's own header (`mywaves%astruct%rxyz`) against the current run's `rxyz` -- it does **not** require anything about "the confinement state" to have been written to disk; it's a pure geometric diff.
- **Two fixes applied during the 2026-09-29 investigation** (present on branch `fix-restart-confinement-damping`, not yet on `devel`):
  1. `set_variables_for_hybrid`: added `confdatarr(:)%prefac = confdatarr(:)%prefac * damping_factor` right after the `set_confdatarr` call, restoring the pre-2015 behavior.
  2. Both `io.f90` and `init.f90` copies of the `tt = exp(...)  - 1.d0` formula: snap `tt` to exact `0.d0` when `max_shift < 1.0d-10`, since `max_shift` from a floating-point position comparison is never bit-exact `0.0` for a genuinely-unmoved restart (typically ~1e-15), and the un-snapped formula leaves `damping` at e.g. `4e-15` -- negligible in energy terms but empirically **not** negligible in effect: it costs several extra outer iterations (see open question) versus a bit-exact `0.0`.
  - Both fixes were verified working exactly as designed (`damping: 0.00E+00`, `mean conf prefac: 0.00E+00` in the log, bit-identical to an explicit `confinement: [0.0, 0.0]` input) -- but did **not** close the remaining restart-vs-reference energy gap. See open question.
- **`reduce_conf`/`ratio_deltas` ramp** (`linearScaling.f90:550-580`): a *separate* mechanism from restart damping, active on every outer iteration once `reduce_conf` becomes `.true.` (set at `linearScaling.f90:661`, after the first iteration). Multiplies the *existing* `confdatarr(:)%prefac` by `input%lin%reduce_confinement_factor` if positive, else by `ratio_deltas**2` (clamped/defaulted per the `ratio_deltas` sign, see kappa below). This is how confinement decays iteration-to-iteration during a normal (non-restart) run; it multiplies whatever's already there, so it can never turn an exact `0.0` into something nonzero.
- `adjust_locregs_and_confinement` (called `linearScaling.f90:442`, only inside the `cur_it_highaccuracy==1` block, itself only reachable for `nlevel_accuracy==2`) is another confinement-adjustment point, irrelevant to hybrid mode.
- Confirmed (by reading every call site of `set_confdatarr`/`set_variables_for_hybrid`/`set_optimization_variables` in `linearScaling.f90`) that for hybrid mode, `confdatarr` is populated exactly **once** per run (at `itout==1`) and never rebuilt from scratch afterward -- the only iteration-to-iteration change is the multiplicative ramp above. So if the fixes above make `prefac` bit-exact `0.0` at `itout==1`, it provably stays exactly `0.0` for the rest of a hybrid-mode run.

## Support-function optimization (`src/modules/get_basis.f90`, subroutine `getLocalizedBasis`)

Per-outer-iteration loop (`iterLoop: do`, starting `get_basis.f90:239`) that applies the Hamiltonian, computes the orthoconstrained gradient, and steps the support functions (DIIS or steepest descent per `hpsitopsi_linear`, `initAndUtils.f90`-adjacent) until convergence or a failure-driven exit.

- **`kappa` is literally `ratio_deltas`** (`get_basis.f90:660`: `call yaml_map('kappa',ratio_deltas,...)`), computed (line 641-654) only when `it>1 .and. (target_function==HYBRID .or. experimental_mode)`, as `ratio_deltas = ediff_best/delta_energy_prev` -- how well the actual energy change matches the model's predicted change. Fed into a 3-entry rolling `kappa_history` (line 666-668) and averaged into `dynamic_convcrit` (line 681-687) for hybrid mode's experimental dynamic-convergence-criterion path.
- **"Fake kappa" is exactly this**: `get_basis.f90:650-654` -- whenever `energy_increased .or. energy_increased_previous` (the last step made the trace/energy worse), `ratio_deltas` is **not** computed from the real energy-change ratio; instead it's hardcoded to `0.5d0`, with `call yaml_warning('use a fake value for kappa')`. So a "fake kappa fallback" is a direct symptom of a failed (energy-increasing) SF-optimization step -- it is **not** a FOE/eigenvalue-bounds concept (verified: `grep -rn "fake" chess/` finds nothing; this language is entirely local to `get_basis.f90`, i.e. support-function optimization, not kernel optimization).
- **DIIS failure recovery**: `get_basis.f90:690-817`. When `energy_increased .and. ldiis%isx==0 .and. .not.allow_increase` (a bad step with no DIIS history to fall back on), the code reverts to the previous support functions/kernel (`recovered_old_kernel=.true.`, restores `lphiold`/`kernel_best`), sets `can_use_ham=.false.`, decrements the iteration counter by 2 to retry (`it=it-2`), and after enough consecutive failures progressively disables orthonormalization (`ortho_on=.false.`) or switches to steepest descent. `ldiis%icountDIISFailureTot`/`icountDIISFailureCons` (initialized `src/linear/orbitalOptimization.f90:346-347`) count these. `nit_exit = min(nit_basis + ldiis%icountDIISFailureTot, nit_basis+6)` (line 844) -- so DIIS failures buy a *few* extra iterations (capped at 6), not unlimited retries.
- In the "no failure" branch, `can_use_ham=.true.` (line 814) -- confirming `can_use_ham`'s value, for hybrid mode where the `linearScaling.f90` override is dead code, is driven entirely by whether the *most recent* SF-optimization step increased the energy.
- **Exit criteria** (`exit_loop(1:7)`, `get_basis.f90:856-869`), each setting `infoBasisFunctions` to a distinct signal: `(1)` net iteration cap `it>=nit_exit` -> `infoBasisFunctions=-1`; `(2)` total iteration cap `it_tot>=3*nit_basis` -> `-2`; `(3)` experimental-mode early-stop energy-difference criterion; `(4)` `fnrm_now<conv_crit` (the normal gradient-norm convergence, sets `infoBasisFunctions=it`, i.e. positive/converged); `(5)` experimental dynamic-criterion path; `(6)` extended-input-guess-only kappa criterion (`itout==0` only); `(7)` dead code (`.false. .and. ...`, always skipped). **`info_basis_functions<=0` is exactly what triggers the `support function optimization not converged` warning** in `print_info` (`linearScaling.f90:2373`) -- i.e. this warning means the SF loop hit an iteration cap (paths 1 or 2) rather than genuinely converging on the gradient norm, which is the downstream consequence of repeated fake-kappa/DIIS-failure cycles eating the iteration budget.
- This directly explains a real bug report's failure signature ("46 fake kappa fallbacks and 8 DIIS failures", ends at `infocode: 1` after hitting the outer-loop iteration cap): the chain is confinement shock (undamped restart confinement suddenly applied to an already-converged basis) -> repeated energy-increasing SF-optimization steps -> fake-kappa fallbacks + DIIS-failure reverts -> SF optimization exhausts its iteration budget without converging (`support function optimization not converged`) -> outer loop's own density residual (`pnrm_out`) never gets small enough either -> hits `itout==nit_lowaccuracy` with `infocode` still at its default `1`.

## Kernel/coefficient optimization (brief -- not deeply traced this session)

Dispatched by `input%lin%scf_mode`: `LINEAR_FOE`, `LINEAR_DIRECT_MINIMIZATION`, `LINEAR_NTPOLY`, or diagonalization (`printSummary`, `linearScaling.f90:2291-2299`, labels `FOE`/`DMIN`/`NTPOLY`/`DIAG`). `info_scf<0` prints `density optimization not converged` (`linearScaling.f90:2386`) -- the kernel-side analogue of `info_basis_functions<=0`, worth checking too when chasing a convergence failure, but distinct from the SF-side symptom above.

FOE itself (Chebyshev fitting of the Fermi function, eigenvalue-bound tracking via `evbounds_nsatur`/`evboundsshrink_nsatur`/`betax_foe`/`fscale`) lives in `chess/` (CheSS library) and was **not** traced in this session beyond confirming the "fake kappa"/DIIS-failure language does not appear there. Given the SF-side mechanism above already fully explains the observed failure signature, tracing CheSS internals is lower priority unless a future investigation specifically implicates the kernel/density-mixing side (`info_scf<0`) rather than the SF side (`info_basis_functions<=0`).

## Open question (as of 2026-09-29, unresolved -- update this section as it's chased further)

With both confinement fixes above applied, a from-scratch reference and a same-geometry restart with **default** (`confinement: [-1.0, 0.0]`, "automatic") confinement were compared against a restart with **explicit** `confinement: [0.0, 0.0]`, on a small test system (SiH4). Both are provably bit-identical in `confdatarr(:)%prefac` (exact `0.0`) at every outer iteration, per the "confdatarr populated once, only ever multiplicatively scaled afterward" fact established above, and confirmed by direct high-precision debug prints during the session. And yet: the explicit-zero restart converges (exits via `check_for_exit`'s `pnrm_out<highaccuracy_conv_crit` branch) after **1** outer iteration, while the fixed-automatic restart takes **4**, landing a genuine ~29 microhartree away from the from-scratch reference (the explicit-zero restart lands much closer). Resolved input echoes for the two runs are identical except the literal `confinement` array value (diffed directly, confirmed). `can_use_ham` is dead code for hybrid mode in both cases, so that's not it either (unless it differs *dynamically* during the run because the actual SF optimization trajectory differs -- see next steps).

Since `confdatarr` itself is ruled out, and the only remaining behavioral difference at the *input* level is the literal `-1.0` vs `0.0` in `input%lin%potentialPrefac_lowaccuracy(itype)` -- a value now confirmed to be read in exactly one place that matters for hybrid mode (nowhere, since `can_use_ham`'s hybrid check is dead) -- the next place to look is **not** confinement-related at all. Concrete next steps for whoever picks this up:
1. Instrument `pnrm_out`/`pnrm` (the kernel-mixing density residual, printed as `delta`/`delta out` in `printSummary`/`print_info`) iteration-by-iteration for both runs -- the exit criterion is purely a threshold on this value, so understanding *why* it's larger after iteration 1 for the automatic-then-zeroed case is the direct question, not anything about confinement magnitude.
2. Check DIIS/mixing history state: a restart always starts with `ldiis%is` reset per `reset_DIIS_history` (`get_basis.f90:261-263`) and empty history, same for both automatic and explicit-zero cases -- confirm this is genuinely identical, but also consider that the very first Hamiltonian application's *numerical* path (not its confinement *value*) could still differ if `input%lin%potentialPrefac_lowaccuracy(itype)` being `-1.0` vs `0.0` is read anywhere else not yet found by grep (re-grep after any future refactor; this is exactly the kind of "read once, forgotten elsewhere" bug pattern this whole investigation has been finding).
3. Consider that this ~29 µHa might simply be irreducible support-function gauge freedom (multiple bases can represent the same physical state, and the optimizer isn't required to land on a bit-identical one) rather than a bug at all -- the original bug report's own best-case zero-confinement restarts were never bit-exact either (0.03 µHa best case, 0.38 mHa for a different restart-format variant). If so, the interesting remaining question is why this gauge noise scales the way it does with system size (documented separately in the restart-confinement investigation notes, not duplicated here), not a further code hunt in this file.
